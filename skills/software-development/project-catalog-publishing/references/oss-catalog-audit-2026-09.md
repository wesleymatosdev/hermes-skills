# Worked audit — 72-entry OSS catalog, 2026-09

Audit of an OSS catalog site (`oss-site`) before a restructure into per-project
sections. Catalog: 72 entries across 8 groups, generated by
`scripts/collect.py` into `data/projects.json`, `www/projects.js`, and
`www/llms.txt`.

Every finding below was independently re-verified by the coordinator against
`gh api` / direct file reads before being acted on — worker reports were treated
as claims, not facts. That step mattered: it is what confirmed the numbers were
exact rather than plausible.

## Finding 1 — ten "local only (coming soon)" entries were already public

`collect.py` enriched curated entries' `stars` from the GitHub API when a repo
name matched, but **never backfilled `url`**. Because the curated table
hardcoded `url: None` from when those repos were local, the catalog advertised
"coming soon" for ten shipped, public repos.

Verification:

```bash
for r in <names>; do
  printf "%-28s private=%s stars=%s\n" "$r" \
    "$(gh api repos/<owner>/$r --jq .private)" \
    "$(gh api repos/<owner>/$r --jq .stargazers_count)"
done
```

All returned `private=false`. Fixed in the pipeline (backfill `url` alongside
`stars`), not in the generated data.

**Transferable lesson:** partial enrichment is worse than none, because it
looks like it ran. If a pipeline backfills any field from an API match, audit
which fields it *doesn't*.

## Finding 2 — five catalog urls pointed at private repos (dead links)

Five entries carried a `url` but verified `private=true`. Every visitor
clicking them got a 404.

**The tell, without any API call:** these were exactly the url-bearing entries
whose `stars` was `null` — the API enrichment never matched them, because the
API does not list private repos. `url != null && stars == null` is a
high-signal dead-link detector in any catalog with this shape.

Fix: an explicit `public: bool` field gating every link and star button.

## Finding 3 — a client name published in three generated files

An entry named `unfit-<clientname>` — a per-client deployed instance of an
internal review tool — appeared in the public catalog. The user flagged the
*name* as wrong; the real problem was larger:

1. it named a private client engagement in a public catalog;
2. the repo was `private=true`, so the link was dead anyway;
3. it was not a project — a deployed instance for one client.

The leak spanned `data/projects.json`, `www/projects.js`, and `www/llms.txt`
(the last existing specifically for AI scrapers to ingest).

**Resolution: dropped, not renamed.** Added to the pipeline's `IGNORE_LOCAL`
set with the reason recorded inline, plus a grep gate in the verification
procedure so it cannot return. Same treatment as an ops repo excluded for
OPSEC.

This was also the *second* surface of one disclosure — a prior security audit
had independently flagged the same client's PII on a demo subdomain. When a
client name leaks in one place, sweep for the others.

## Finding 4 — four overclaims that would have become public lies

| project | README claim | reality |
|---|---|---|
| screen recorder | "cross-platform" | FFmpeg encoder hardcoded to macOS-only `h264_videotoolbox` (`src/main.rs:105`), no fallback — would fail on Linux/Windows |
| console-art lib | `npm install @<scope>/<pkg>` | package 404s on **both** npm and JSR — unpublished despite `0.1.0` in manifests |
| skills catalog | "battle-tested in real agent loops" | no artifact in the repo evidences it |
| group blurb | "Forks kept alive with real work on them" | both members 0 commits ahead of upstream (73 and 5 *behind*) |

Also: both forks' catalog descriptions were the upstream projects' own README
text, which on a personal OSS catalog reads as claimed authorship.

The counter-example worth imitating was already in the catalog — one repo whose
README opens: *"Status: proof of concept, unmaintained. We recommend using
[X] instead."* That entry needed no fixing.

## Finding 5 — a hello-world catalogued as a CLI tool

One entry was listed as a CLI tool. Its entire `src/main.rs`:

```rust
fn main() {
    println!("Hello, world!");
}
```

No README. Dropped from the catalog until it has substance. **Read the entry
point; a plausible name and a Cargo.toml prove nothing.**

## Finding 6 — star affordance research

- `github.com/<owner>/<repo>/stargazers` returns GitHub's 404 page. Verified on
  both a personal repo and `microsoft/vscode` — it is a global removal, not a
  permissions artifact. Never link it.
- No separate "star intent" URL exists. The repo page hosts the Star control;
  logged out, clicking it routes through `github.com/login?return_to=<repo>`.
- `ghbtns.com` (the official-buttons iframe host) served
  `last-modified: Mon, 12 Dec 2022` — effectively unmaintained, and one
  third-party request per button.
- `api.github.com` does send `access-control-allow-origin: *` with
  `x-ratelimit-limit: 60` unauthenticated, so a client-side count *works* — but
  costs a rate-limited third-party request per visitor.
- A well-known third-party skills catalog's "star" button turned out to be a
  **Firebase Firestore like-counter** (anonymous auth + `FieldValue.increment`),
  not a GitHub star at all. Worth knowing before copying a pattern that looks
  native.

Chosen: plain anchor + build-time `stargazers_count`. At audit time every repo
had 0 stars except one with 3 — so a "live" count would have added nothing over
the cached one, and the zero state needed designing anyway.

## Finding 7 — scope check before layout

The ask was "a section for each project." With 72 entries, ~40 of them
learning/archive repos (advent-of-code, kafka exercises, hangman), a uniform
per-entry layout would have buried the actual portfolio.

Resolved as **21 full sections + compact rows for the rest**, proposed entry by
entry with a one-line justification per full-section pick, for the user to
approve. Full = the agent-infra work, the CLI family, libraries, benchmarks.

## Pipeline gaps found along the way

- The local-repo walk covered only one parent directory, so a public repo
  living outside it was invisible to the collector and needed an explicit
  curated entry.
- No ignore mechanism existed for deliberately-absent local directories, so
  upstream clones emitted a warning on every single run — training the operator
  to ignore warnings.
- Working tree had an uncommitted regeneration diff (`generated` date + stars
  null→0) at audit start. Baseline-commit that before layering changes, or the
  real diff becomes unreviewable.
